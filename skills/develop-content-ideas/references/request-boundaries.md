# Request boundaries

Read before prep when a request refers to earlier ideas, changes constraints, or specifies quantity
or language. Resolve intent before constructing the request; do not make the user restate known data.

| Request | Operation and preserved constraints |
| --- | --- |
| N more like this / like number N | Bind the unique relevant example in the real visible list or original IdeaSet. Preserve mechanism and restrictions; substitute only the permitted elements. |
| Change the style/mechanism/platform | Latest explicit instructions override those dimensions only. Carry forward unchanged restrictions; do not force the old mechanism against the user's request. |
| Select N / revise N | Reuse the exact displayed number, title and retained ID. Revise only requested fields; do not regenerate the other candidates or invent IDs when recovering chat. |
| Pick a few / briefly explain | Select from the existing validated list; preserve original numbers. Use `references/delivery.md` to render and emit the selection, not a new batch. |
| Another batch | A new run with the real earlier list/context, current count and exclusions; avoid unwanted repeats, not the shared causal scaffold. |

Resolve against the nearest relevant list plus later corrections, not merely the last text block.
With several possible referents, inspect the visible context first; ask one focused question only
if ambiguity remains. Ask for missing/invalid-number context rather than combining unrelated lists.
Streamed fragments belonging to one message may be joined exactly; never merge across user turns.
Chat context supports creative continuity, not verified metrics, personal facts or external research.

## Quantity

Shortlists accept 1–20 ideas per run. Honor explicit counts (including one or two); do not turn a
one-idea request into `rework_content`, which means revising existing content with its own contract.
If no count is given, use a stated small default such as five rather than claiming the user specified
it. If counts conflict, use the latest explicit instruction or clarify a remaining contradiction.
Above twenty, disclose the per-run limit and ask about batching; never silently deliver fewer or
reset a failed run to evade the revision budget. “Pick three” does not mean “generate three new”.

## Language and source

Apply `report-language.md`. Keep quoted source text verbatim even if the report language changes;
`direct_topic` is a literal topic from this turn, not its translation. Otherwise use the bound
conversation/previous-list route. Do not rewrite the current user request to smuggle in history.
A language change alone does not change the selected candidate, causal mechanism or evidence.

## Semantic review before core

For a selected-example variation, compare **each completed candidate** against the source and the
latest instruction. Identify the fixed relationship, the allowed change and that item's concrete
substitution. Check its title, opening and filming direction, not just the batch introduction.
Record a compact per-candidate comparison in the existing `overview.portfolio_logic` (candidate ID,
replacement, progression and unchanged goal); no new schema field is needed. Fix a changed link or
missing concrete element within the same authoring pass. Explicitly requested changes belong in
that comparison and must not be treated as accidental drift. Do not invent a fixed numerical cost
or resource requirement absent from the source; mark proposed tuning as hypothetical.

The script checks counts, references, IDs, fields and final-file integrity. It cannot determine
whether the selected example is right, whether a translation is accurate or whether a causal
mechanism is preserved. Do not claim a successful schema check proves these semantic judgments.
